## FUNDAMENTAL DIFFERENCE FROM SUBPHASES 1–4 — READ FIRST

**Subphases 1–4 controlled what process launches and what its command line says.
Subphase 5 controls what Windows API calls are made: OpenProcess, LoadLibrary,
CreateRemoteThread. These require ACTUAL OS API invocations.**

Three distinct mechanisms are required:

| EID | API | Mechanism |
|---|---|---|
| EID-10 (ProcessAccess) | OpenProcess | Python ctypes — called directly from the simulation script |
| EID-7 (ImageLoad) | LoadLibraryW | ctypes.WinDLL() + LOLBin subprocesses loading unsigned DLL |
| EID-8 (CreateRemoteThread) | CreateRemoteThread | subprocess PowerShell with P/Invoke Add-Type |

**Why not use PowerShell for EID-10?** PowerShell process-management cmdlets
(`Get-Process`, `Stop-Process`, `Start-Process`) call OpenProcess with broad access via
.NET's `System.Diagnostics.Process` class. Their call_trace CONTAINS the Automation DLLs.
The E2 fix in `api_memory.yaml` uses `call_trace not_contains_any` to suppress these.
Direct P/Invoke from PowerShell would work, but Python ctypes is simpler and avoids
any Add-Type compilation noise. Source image for EID-10 = python.exe (not excluded).

**Why subprocess PowerShell for EID-8?** The simulation script (python.exe) is excluded
from `API_CRT_SUSPICIOUS_SOURCE_001` via `source_image not_contains "python_runtime\python.exe"`.
A subprocess `powershell.exe` is the source — it IS in the suspicious-source allowlist.

### E5 workaround — MANDATORY for EID-8
Sysmon's `sysmonconfig-export.xml` has `<StartModule condition="is">C:\Windows\system32\kernel32.dll</StartModule>`
as an unconditional CreateRemoteThread exclusion. Any CRT whose thread start address
resolves inside kernel32.dll (e.g. LoadLibraryA) is silently dropped by Sysmon.
**All EID-8 simulations must use `RtlExitUserThread` from `ntdll.dll` as the CRT start address.**
Resolving via: `GetModuleHandle("ntdll.dll")` → `GetProcAddress(hNtdll, "RtlExitUserThread")`.
This avoids kernel32.dll, avoids real payload execution (thread terminates immediately), and
is confirmed working from the prior Phase 7A Subphase 6 session (2026-08-10).

### E1/E2 CLOSED
`api_memory.yaml` now has source_image exclusions for `conhost.exe` and `cmd.exe` (E1),
target_image exclusions for `csc.exe` and `cvtres.exe` (E1), and call_trace exclusions for
PowerShell Automation DLLs (E2). The Add-Type compiler cascade generated by the EID-8
subprocess PowerShell will NOT contaminate API_OPEN_PROCESS_VM_WRITE_001. No workaround needed.

### EID-8 launch timeout
`launch_argv()` uses `timeout=20`. PowerShell Add-Type compilation takes 5–15 seconds.

will be captured by poll window"` — NOT the generic EID-1 message. Implement this by checking

### `ctypes_open_process` — NEW helper for EID-10 simulation
```python
def ctypes_open_process(access: int, pid: int, label: str) -> bool:
    """
    Call OpenProcess(access, False, pid) via ctypes. Closes handle if acquired.
    Returns True if handle was acquired (EID-10 generated), False otherwise.
    """
    print(f"  [CTYPES] {label}")
    print(f"  [CALL]   OpenProcess(access=0x{access:08x}, pid={pid})")
    if pid == 0:
        print(f"  [WARN]   PID is 0 — target process not found, skipping")
        time.sleep(1)
        return False
    h = _k32.OpenProcess(access, False, pid)
    if h:
        _k32.CloseHandle(h)
        print(f"  [CTYPES] Handle acquired and released — EID-10 expected")
        time.sleep(2)
        return True
    else:
        err = ctypes.get_last_error()
        print(f"  [CTYPES] OpenProcess failed (WinError {err}) — EID-10 may still be logged by Sysmon at NtOpenProcess syscall level")
        time.sleep(2)
        return False
```

### Note on EID-7 DLL loading strategy
**Do NOT use ctypes.WinDLL() from within the simulation script for Rule 5.**
Windows `LoadLibraryW` path-caches DLLs per-process: a second call on the same path
from the same process does NOT re-invoke `LdrLoadDll` — it only increments the
reference count. Sysmon EID-7 fires at the `LdrLoadDll` hook, so only ONE EID-7
would be generated per DLL path per process, regardless of how many times
`ctypes.WinDLL(path)` is called on that path.

**Correct approach for Rule 5:** launch subprocess python for EACH "launch" event.
Each subprocess is a fresh Windows process with its own DLL cache. Each subprocess
calling `ctypes.WinDLL(path)` generates an independent EID-7. Use:
```python
PYTHON = sys.executable  # defined in BLOCK 0
```

Each Rule 5 "launch" is:
```python
launch_argv(
    [PYTHON, "-c", f"import ctypes; ctypes.WinDLL(r'{dll_path}')"],
    label
)
```

This is safe: no argtypes issues, no FreeLibrary complexity. Each subprocess
is an independent Windows process. image_loaded = the dll_path. image = python.exe
(not in Rule 6 LOLBin list, so only Rule 5 fires — no cross-fire). ✓

`PYTHON = sys.executable` is already defined in BLOCK 0. Use it directly.

### `get_pid_by_name` — NEW helper for PID resolution
```python
def get_pid_by_name(name: str) -> int:
    """Return first PID matching image name via tasklist /fo csv. Returns 0 if not found."""
    try:
        out = subprocess.run(
            ["tasklist", "/fo", "csv", "/fi", f"imagename eq {name}"],
            capture_output=True, text=True, timeout=10
        )
        for line in out.stdout.strip().splitlines():
            if line.startswith('"') and name.lower() in line.lower():
                return int(line.split(",")[1].strip('"'))
        return 0
    except Exception as e:
        print(f"  [WARN]   get_pid_by_name({name!r}) failed: {e}")
        return 0
```
